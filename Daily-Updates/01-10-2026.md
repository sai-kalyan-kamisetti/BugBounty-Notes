## 1. JavaScript Sinks — Code Execution vs HTML Injection

- Learned the core distinction between two sink categories:
  - **Code-execution sinks** (`eval()`, `new Function()`, `setTimeout("...")`, `setInterval("...")`) — take raw JS as a string, no HTML parser involved. Payload = plain JS (`alert(1)`), not `<script>` tags.
  - **HTML-injection sinks** (`document.write()`, `document.writeln()`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`) — take a string and run it through the HTML parser. Payload needs real HTML markup.
- Key gotcha: `innerHTML` / `outerHTML` / `insertAdjacentHTML` **do not execute** `<script>` tags — the browser spec marks script elements created this way as inert. Explains why `<script>alert(1)</script>` can silently do nothing in some contexts.
- `document.write()` **does** execute `<script>` tags, but only while the document is still being parsed (synchronous, during initial page load).
- For inert-script contexts, use event-handler-based payloads instead: `<img src=x onerror=alert(1)>`, `<svg onload=alert(1)>`.

## 2. Where to "close the tag" vs inject directly

- Depends on what the sink is concatenating input into, not just the sink type:
  - Input landing **inside an existing attribute** → break out first: `"><script>alert(1)</script>`
  - Input landing in **open HTML body context** (no tag to close) → inject fresh tag directly: `<img src=x onerror=alert(1)>`
  - Input landing inside `eval()` → no HTML at all, just JS: `alert(1)`

## 3. Why "correct-looking" payloads sometimes fail

- Common causes reviewed:
  - Quote mismatch (single vs double quotes in the actual attribute)
  - Server/app HTML-entity-encoding input before insertion
  - Wrong sink assumption (e.g. actually going through `textContent` or an auto-escaping template engine)
  - CSP blocking inline script execution
- Recommended workflow: set DOM/event-listener breakpoints in DevTools on the suspected sink to see exactly what string hits it.

## 4. Case Study — Starbucks HackerOne XSS reports (public disclosure)

- Analyzed two real disclosed payloads targeting `starbucks.com/account/(A(...))/signin` and `(F(...))/signin`.
- Identified the encoding technique as **double URL encoding** (percent-encoding applied twice) — a classic WAF/filter-bypass technique that defeats filters which only decode input once.
- Decoded payload #1 (two passes): `" /onmouseover="alert(document.domain)"` — classic attribute-breakout PoC.
- Decoded payload #2 (two passes): `" /onmouseover="alert(document.getElementsByName('Account.PassWord')[0].value)"` — stronger PoC demonstrating live credential-field exfiltration on the sign-in page.
- Root cause identified: the `(A(...))` / `(F(...))` URL segment is **ASP.NET's legacy cookieless session ID munging syntax**, which the app reflected back into the page unsanitized — a known historical ASP.NET XSS vector.
